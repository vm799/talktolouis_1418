# ADR-001: Voice-First Event-Logged Coordination System

**Status:** Accepted  
**Date:** 2026-05-02  
**Deciders:** Vaishali Mehmi

---

## Context

Real-world workflows unfold over time, not within a single interaction.
Traditional chat-based systems fail to:
- Maintain continuity across sessions
- Coordinate responses based on prior events
- Ensure deterministic and safe behaviour

This creates a need for:
- A persistent record of user interactions
- State-aware response coordination
- Reliable behaviour under interruption

---

## Decision

We implement a **voice-first, event-logged coordination system** using MongoDB as the persistent memory layer.

---

## Architecture Overview

### 1. Event-Logged Memory (MongoDB)

- All interactions are stored as immutable events
- Events are append-only and timestamped
- State is derived dynamically from event history at runtime

This enables:
- Auditability
- Reproducibility
- Session recovery

---

### 2. Decomposed Agentic Pipeline

The system is implemented as a **single service with logically separated responsibilities**, rather than physically distributed agents.

| Logical Role | Implementation | File |
|-------------|----------------|------|
| Input Agent | Speech-to-text (LiveKit/Deepgram) | `agent-py/src/agent.py` |
| Intent Router | Rule-based + AI classification | `louis_service.py` (assess_question) |
| Safety Layer | Red-flag keyword detection | `louis/red_flag_detector.py` |
| State Handler | Event-derived state logic | `mongo_event_repo.py.derive_state()` |
| Action Layer | Deterministic template selection | `response_templates.py` |
| Output Agent | Text-to-speech (voice output) | `louis/elevenlabs_wrapper.py` |

This provides **agent-like coordination without distributed complexity**.

---

### 3. Constrained AI Usage

- AI is used **only for intent classification**
- AI does not generate final responses
- All outputs are deterministic templates

This ensures:
- Safety
- Predictability
- Compliance with hackathon constraints

---

### 4. State Model

- Runtime state is derived from MongoDB events via `derive_state()`
- No reliance on in-memory state for correctness
- System can reconstruct behaviour after interruption

This demonstrates **prolonged coordination via event replay**.

---

### 5. Voice-First Interaction Model

- After pharmacological dilation, patients cannot safely read screens. Voice is the only viable interface for post-screening coordination.
- Voice access is a clinical accessibility necessity, not a UX preference
- No reliance on screen-based UI interaction during the post-screening window

---

## Consequences

### Benefits
- High reliability in live demo conditions
- Clear demonstration of MongoDB as a context engine
- Strong alignment with coordination and stateful workflows
- Safe and deterministic outputs

### Trade-offs
- Limited conversational flexibility
- Reduced generative capability
- Simplified agent abstraction (logical vs distributed)

---

## Alternatives Considered

### 1. Fully Generative LLM Responses
Rejected:
- Unsafe (unpredictable language to patients)
- Unpredictable outputs
- Violates compliance requirements

### 2. Full Multi-Agent Distributed System
Rejected:
- Over-engineered for hackathon timeframe
- Unnecessary for demonstrating coordination

### 3. Pure Rule-Based System (No AI)
Rejected:
- Lacks adaptability
- Fails "agentic" criteria

---

## Phase 2 (Future Architecture)

- Full event sourcing (state reconstructed entirely from event streams)
- Distributed multi-agent coordination
- Cross-session orchestration
- Adaptive retrieval across external sources

## Summary

This system prioritises **deterministic coordination, safety, and reliability**, while demonstrating how MongoDB can function as a persistent event-based memory layer for agentic workflows. The result is a **coordination engine** in which AI interprets intent and the system executes deterministic coordination logic using event history.
